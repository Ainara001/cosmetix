# Синхронизация цен и наличия: PostgreSQL → API → приложение → SQLite

Состояние на 2026-11-08. Документ описывает, что реально работает, чем это проверено
и что **не** сделано.

## Путь данных

1. Человек вводит **проверенное** предложение магазина в админ-панели (`/admin`, вкладка
   предложений, PR #38) или через `PUT /admin/api/offers`. В PostgreSQL это таблица
   `store_offers` (миграция `002_store_offers.sql`): цена (может быть пустой), наличие,
   ссылка и её тип, источник, способ, статус проверки, дата проверки, кто проверил. Каждое
   изменение пишется в `admin_audit`.
2. Сервер отдаёт **публичный снимок** `GET /v1/catalog/offers`: только предложения со
   статусом `verified`, товары и магазины названы по `brand + name` и `name + address`
   (не по внутренним id). Не требует входа и согласия; в запросе нет данных пользователя.
3. Приложение (`OfferSyncService`) читает снимок через `ServerHttp` (повторы только для
   идемпотентного GET, без редиректов, 5 МБ максимум) и записывает его в SQLite
   (`OfferSyncRepository.apply`) **одной транзакцией**: прежняя копия (`origin='server'`)
   заменяется целиком. Поэтому: нет дублей; снятое/отозванное/изменённое на сервере
   исчезает или обновляется; при ошибке посреди записи старая копия остаётся.
4. Одна неверная строка портит весь снимок: тогда **ничего** не применяется (приложение и
   сервер не согласны по формату). Неизвестный товар или магазин пропускается и
   считается (`skippedUnknownProduct` / `skippedUnknownStore`).
5. Предложение, введённое на самом телефоне (`origin='local'`), синхронизация не трогает;
   при совпадении товара и магазина побеждает локальное.
6. Карточка товара и «Сравнение цен» читают только `verified` предложения с ценой. Свежесть
   — 2 дня: старее показывается как «Цена на момент последней проверки: дата». Нет
   подтверждённой цены — «Цена не подтверждена». Под ценами строка «Цены обновлены: дата»,
   кнопка обновления и сообщение, если обновить не удалось (тогда видна последняя копия).
7. Ссылка «Посмотреть товар в магазине» показывается только для магазина, у которого в
   `assets/catalog/source_policy.json` стоит `links: allowed`. Сейчас такого магазина **нет**.

## Когда синхронизация идёт

Только если задан адрес сервера (`--dart-define=AI_BASE_URL=...` или настройки ИИ): при
запуске и по кнопке. Без адреса приложение не делает ни одного сетевого запроса.

## Что проверено (запуски в этой ветке)

* `server`: 108/108 тестов с PostgreSQL, включая `GET /v1/catalog/offers`.
* Flutter: `test/offer_sync_test.dart` (13 проверок: заполнение, нет дублей, замена цены,
  отзыв, пустая цена, нет сети, 500/мусор/плохая строка, неизвестный товар и магазин,
  локальное предложение не трогается, нет адреса — нет запросов, данные пользователя не
  меняются, провайдер, миграция v17→v18 на файловой БД).
* Сквозной сценарий `tool/e2e_offer_sync.sh` (реальный PostgreSQL, реальный сервер,
  админ-API, файловая SQLite, приложение): 7 шагов — пустой каталог; проверенное
  предложение → цена на карточке и открытие сохранённого адреса; смена цены → повторная
  синхронизация без дубля; повтор; отзыв на сервере → исчезло; снова проверено → вернулось;
  сервер остановлен → видна последняя копия с датой. Все 7 прошли.

```bash
PG_URL_BASE=postgres://user@127.0.0.1:5432 tool/e2e_offer_sync.sh
```

Скрипт создаёт и удаляет собственную временную базу, поднимает сервер на порту
`E2E_PORT` (8799) и останавливает ровно свой процесс. Предложение в нём — **тестовые
данные** (в источнике `TEST DATA`), с коммерческими данными не смешивается.
Ссылка в шаге 1 проверяется с **тестовой** политикой, разрешающей магазин; с настоящей
политикой в тесте проверено, что ссылки нет.

## Чего нет (честно)

* Реальных проверенных предложений магазинов — **0**. Данные должен вводить человек,
  который посетил магазин или имеет разрешённый фид.
* Разрешённых рабочих ссылок на магазины — **0** (все магазины `unconfirmed`, см.
  `docs/data-sources-terms.md`).
* Парсеров магазинов нет и не планируется без письменного разрешения.
* Запуск на настоящем телефоне/Appetize с реальным сервером не выполнялся в этой ветке.
